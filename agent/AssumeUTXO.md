# AssumeUTXO in Blackcoin More

> **Status:** Infrastructure inherited and PoS-compatible, not yet activated. One code change required + one operational step.
>
> **Authored from:** Deep source diff of `blackcoin-more-284` vs `bitcoin-core-284`.

---

## 1. What Is AssumeUTXO?

AssumeUTXO allows a new full node to become operational almost instantly. Instead of validating every block from genesis (Initial Block Download — IBD), a node loads a serialized snapshot of the Unspent Transaction Output (UTXO) set at a specific block height whose hash is hardcoded into the software. The node participates in the network immediately while a background process validates all historical blocks.

The feature has three components:
1. **A hardcoded commitment** (`AssumeutxoData`) in `chainparams.cpp` — a block height, block hash, coin count, and hash of the serialized UTXO set.
2. **A UTXO snapshot file** — generated by a fully synced node using the `dumptxoutset` RPC.
3. **Two concurrent `Chainstate` objects** managed by `ChainstateManager` — a "snapshot" chainstate syncing from the tip, and an "IBD" chainstate validating historical blocks in the background.

---

## 2. Why This Matters More for Blackcoin Than Bitcoin

IBD is inherently more expensive for Blackcoin than for Bitcoin:

- **Bitcoin (PoW):** Validating a historical block checks the PoW header hash and transaction signatures. No UTXO lookups are needed to validate the consensus mechanism itself.
- **Blackcoin (PoS):** Validating a historical PoS block requires a **UTXO database lookup** for the Coinstake input to confirm the staker owned the coins and to run the kernel check (`CheckKernel` in `src/pos.cpp`). This is precisely why `CheckBlock` in Blackcoin takes a `Chainstate&` parameter that Bitcoin Core's version does not.

With 5.9M+ blocks accumulated over 10 years, new nodes must perform millions of UTXO lookups during IBD. AssumeUTXO bypasses this entirely for new users and stakers.

### 3.2 `src/kernel/coinstats.cpp` — UTXO Hash Encoding (Already Correct)

The hash committed to in `AssumeutxoData::hash_serialized` is computed by `TxOutSer()`. The encoding uses 2 bits for output-type flags to cover all three output types Blackcoin produces:

```cpp
// Bit 0 = fCoinBase  (PoW coinbase output)
// Bit 1 = fCoinStake (PoS coinstake output)
// Bits [31:2] = nHeight
ss << static_cast<uint32_t>((coin.nHeight << 2) | (coin.fCoinBase ? 1u : 0u) | (coin.fCoinStake ? 2u : 0u));
ss << coin.out;
```

This produces three unambiguously distinct code words:

| Output type | fCoinBase | fCoinStake | Code (height=100) |
|---|---|---|---|
| Regular transaction | 0 | 0 | `400` |
| PoW coinbase | 1 | 0 | `401` |
| PoS coinstake | 0 | 1 | `402` |

**Why this matters per network:**

- **Mainnet:** PoW ended at block `10000` (`nLastPOWBlock = 10000`). Blocks 1–10000 produced PoW coinbase outputs (`fCoinBase=1`). All block rewards from block 10001 onward are PoS coinstake outputs (`fCoinStake=1`). A Mainnet snapshot will contain all three output types, and the hash commitment correctly distinguishes every one.

- **Testnet / Regtest:** Both run hybrid PoW+PoS with `nLastPOWBlock = 0x7fffffff` (effectively unlimited). A Testnet snapshot will have PoW and PoS blocks interleaved throughout. The 2-bit encoding handles this correctly — a PoW coinbase and a PoS coinstake at the same height will hash to different values.

> **IMPORTANT:** This encoding is designed for Blackcoin's own internal requirements. Bitcoin compatibility is irrelevant. **Do not change this encoding** — any modification invalidates all distributed snapshots and breaks the hash comparison that `MaybeCompleteSnapshotValidation` relies on.

### 3.3 `src/coins.h` — The `Coin` Struct Serialization (Already Correct)

Blackcoin's `Coin` struct carries two extra fields not in Bitcoin Core: `fCoinStake` and `nTime`.

**Bitcoin Core `Coin` serialization:**
```cpp
// Fields: nHeight (shift 1), fCoinBase (bit 0)
uint32_t code = nHeight * uint32_t{2} + (fCoinBase ? 1 : 0);
::Serialize(s, VARINT(code));
::Serialize(s, Using<TxOutCompression>(out));
```

**Blackcoin `Coin` serialization:**
```cpp
// Fields: nHeight (shift 2), fCoinBase (bit 0), fCoinStake (bit 1)
uint32_t code = nHeight * uint32_t{4} + (fCoinBase ? 1 : 0) + (fCoinStake ? 2 : 0);
::Serialize(s, VARINT(code));
::Serialize(s, VARINT(nTime));   // Extra: tx timestamp for PoS kernel checks
::Serialize(s, Using<TxOutCompression>(out));
```

When `dumptxoutset` writes the snapshot, every `Coin` includes `fCoinStake` and `nTime`. When `loadtxoutset` deserializes it, those fields are fully restored. `CheckKernel` in `pos.cpp` can then use `coin.nTime` for kernel validation. **No changes needed.**

### 3.6 `src/validation.cpp` — `MaybeCompleteSnapshotValidation` (Background Verification)

After the IBD chainstate catches up to the snapshot base height, this function computes the UTXO set hash of the fully-validated IBD chainstate and compares it to `AssumeutxoData::hash_serialized`. This is the security-critical step.

Hash computation uses `ComputeUTXOStats` -> `TxOutSer`, which is PoS-aware (encodes `fCoinStake`). The final hash correctly reflects the full Blackcoin UTXO set including coinstake metadata. **No changes needed.**

`loadtxoutset` validates these bytes during deserialization, preventing a Bitcoin snapshot from loading on a Blackcoin node or a Testnet snapshot loading on Mainnet. **Already works correctly.**

## 4. PoS Protocol Version Compatibility Analysis

Blackcoin has four distinct PoS protocol eras activated by **block timestamp**, not block height. Every era has different coinstake validation rules. AssumeUTXO must be compatible with all of them, since a snapshot at any height after block 10000 will have UTXOs that were created under multiple protocol versions.

### Protocol Version Timeline (Mainnet)

| Version | Activation timestamp | Approx date | Activation check |
|---|---|---|---|
| **v2** | `> 1407053625` | Aug 2014 | `IsProtocolV2(nTimeBlock)` |
| **v3** | `> 1444028400` | Oct 2015 | `IsProtocolV3(nTimeBlock)` |
| **v3.1** | `> 1713938400` | Apr 2024 | `IsProtocolV3_1(nTimeTx)` |

Note: all checks use the **block/tx timestamp**, not the block height. UTXOs from any era can coexist in the UTXO set and be spent in any future block.

---

### 4.1 PoS v2 — Timestamp Mask Enforcement

**Activation:** block timestamp `> 1407053625`

**What changed in v2:**
```cpp
// pos.cpp: CheckCoinStakeTimestamp()
if (params.IsProtocolV2(nTimeBlock))
    return (nTimeBlock == nTimeTx) && ((nTimeTx & params.nStakeTimestampMask) == 0);
else
    return (nTimeBlock == nTimeTx);
```

- Block timestamps must align to a 16-second mask (`nStakeTimestampMask = 0xf`).
- Coinstake tx timestamp must equal the block timestamp exactly.
- Pre-v2 blocks only required `nTimeBlock == nTimeTx` with no mask.

**Impact on snapshot:** v2-era UTXOs (`coin.nTime > 0` for v1 transactions) are stored verbatim in the snapshot. When the snapshot chainstate tries to stake with one of these UTXOs in a new block, `CheckCoinStakeTimestamp` is called against the **new block's timestamp** (which is always post-v2 on mainnet), so the mask check applies correctly. No issues.

---

### 4.2 PoS v3 — Fixed Subsidy, Full Kernel Enforcement

**Activation:** block timestamp `> 1444028400`

**What changed in v3 (three separate things):**

**1. `CheckProofOfStake` is now enforced in `ConnectBlock`:**
```cpp
// validation.cpp line 2517
if (block.IsProofOfStake() && params.GetConsensus().IsProtocolV3(block.GetBlockTime())
    && !CheckProofOfStake(pindex->pprev, *block.vtx[1], block.nBits, state, view,
                          block.vtx[1]->nTime ? block.vtx[1]->nTime : block.nTime)) {
    return false;
}
```
Pre-v3 PoS blocks are **not kernel-checked** during `ConnectBlock`. They were validated at the time they were produced, but historical validation in background IBD skips the kernel check for them. This is correct and intentional — pre-v3 kernel parameters used coin age which requires historical data not easily available.

> **IMPORTANT for AssumeUTXO:** The background IBD chainstate will skip `CheckProofOfStake` for pre-v3 PoS blocks (blocks from the PoS era starting ~block 10001 up to the v3 activation around 2015). This is the existing behaviour and requires **no changes**.

**2. Fixed block subsidy replaces coin-age-based rewards:**
```cpp
// coinstatsindex.cpp line 222
if (block.is_pos && !Params().GetConsensus().IsProtocolV3(block.data->nTime)) {
    // Pre-v3: variable reward = coinstake output - coinstake input
    effective_subsidy = (m_total_coinstake_amount - coinstake_before)
                      - (m_total_coinstake_input_amount - coinstake_input_before);
} else {
    // v3+: fixed subsidy from GetBlockSubsidy()
    effective_subsidy = block_subsidy;
}
```
Pre-v3 coinstake rewards are variable and based on coin age. The `CoinStatsIndex` already handles this distinction. The snapshot hash is computed over UTXOs, not over subsidy accounting — this difference **does not affect the snapshot hash**.

**3. Script flags `CHECKLOCKTIMEVERIFY` and `NULLDUMMY` are enforced:**
```cpp
// validation.cpp line 2431
if (consensusparams.IsProtocolV3(block_index.GetBlockTime())) {
    flags |= SCRIPT_VERIFY_CHECKLOCKTIMEVERIFY;
    flags |= SCRIPT_VERIFY_NULLDUMMY;
}
```
Applies to transaction validation in `ConnectBlock` during background IBD. No UTXO snapshot implications.

**`nTime` and kernel hash input for v3:**
```cpp
// pos.cpp line 103 — the kernel hash is:
ss << nStakeModifier << blockFromTime << prevout.hash << prevout.n << nTimeTx;
```
`blockFromTime` is resolved as: `coinPrev.nTime ? coinPrev.nTime : blockFrom->nTime`.
- For **v1 tx UTXOs** in the snapshot: `coinPrev.nTime` is the original tx timestamp. ✅
- For **v2+ tx UTXOs** (`nTime == 0`) in the snapshot: falls back to `blockFrom->nTime`, the block timestamp retrieved from the block index (populated during header sync). ✅

---

### 4.3 PoS v3.1 — Min Fee + Correct Maturity

**Activation:** tx timestamp `> 1713938400` (April 2024)

**What changed in v3.1 (two things):**

**1. Coinstake/coinbase maturity now uses the consensus parameter:**
```cpp
// tx_verify.cpp line 185
if ((coin.IsCoinBase() || coin.IsCoinStake()) && nSpendHeight - coin.nHeight <
    (IsProtocolV3_1(nTimeTx) ? consensus.nCoinbaseMaturity : Params().nCoinbaseMaturity)) {
```
Pre-v3.1: maturity was read from `Params().nCoinbaseMaturity` (a legacy path).
Post-v3.1: maturity is read from `consensus.nCoinbaseMaturity` (the correct, consensus-enforced value).

Both values are `500` on Mainnet, so this is a code-path unification, not a consensus change in practice. **No snapshot implications.**

**2. Minimum transaction fee is enforced:**
```cpp
// tx_verify.cpp line 217
if (IsProtocolV3_1(nTimeTx) && txfee_aux < GetMinFee(tx, nTimeTx))
    return state.Invalid(TX_CONSENSUS, "bad-txns-fee-not-enough");
```
This applies to transactions in the mempool and in new blocks. It does not apply during historical `ConnectBlock` of pre-v3.1 blocks. **No snapshot implications.**

---

### 4.4 `nTime` in UTXOs Across All Protocol Versions

This is the single field most affected by the protocol split. The kernel hash formula always includes `blockFromTime`, which is resolved per-coin:

```cpp
// pos.cpp lines 180, 218, 251 — consistent across CheckProofOfStake, CheckKernel, CacheKernel:
(coinPrev.nTime ? coinPrev.nTime : blockFrom->nTime)
```

| UTXO origin | `coin.nTime` in snapshot | `blockFromTime` resolution |
|---|---|---|
| v1 transaction | Original `tx.nTime` (non-zero) | Uses `coin.nTime` directly |
| v2+ transaction | `0` (tx has no `nTime` field) | Falls back to `blockFrom->nTime` from block index |

Block index entries for all historical blocks are populated during header sync, which completes before `loadtxoutset` can be called. The fallback path is always available. **No special handling needed.**

---

### 4.5 Coinstake Maturity and the Snapshot Boundary

All UTXOs in the snapshot carry `coin.nHeight` — the height at which the transaction was confirmed. Maturity checks in `ConnectBlock` and `tx_verify.cpp` compare against the current block height:

```cpp
pindexPrev->nHeight + 1 - coinPrev.nHeight < consensus.nCoinbaseMaturity  // = 500
```

A coinstake UTXO at the snapshot height that has not yet matured will still show `coin.nHeight` from the snapshot, and the maturity check will correctly block it from being staked until 500 blocks have elapsed from its creation height. **No issues.**

---

### 4.6 No Pruning — IBD Validation Is Always Complete

Blackcoin explicitly disables pruning. During background IBD, the IBD chainstate validates every historical block — including pre-v3 PoS blocks (which skip `CheckProofOfStake`) and post-v3 PoS blocks (which require the full kernel check with UTXO lookup). The IBD chainstate has its own `CoinsViews` hierarchy, completely independent of the snapshot chainstate. **No issues.**

A wrong hash either blocks the feature (harmless) or, in an adversarial scenario, could validate an invalid UTXO set (catastrophic).

### 5.2 Operational Steps to Generate the Snapshot Data

1. **Run a fully synced Blackcoin Mainnet node** with IBD complete and no ongoing reindex.

2. **Choose a snapshot height** — a round number well past the last hardfork (`5930110`) and at least 2000 blocks behind the current tip.

3. **Generate the snapshot:**
   ```bash
   blackcoin-cli dumptxoutset /path/to/utxo-blk<HEIGHT>.dat
   ```
   Record all values from the returned JSON:
   ```json
   {
     "coins_written": 12345678,
     "base_hash":     "00000000000...",
     "base_height":   6000000,
     "txoutset_hash": "aabbcc...",
     "nchaintx":      17000000
   }
   ```

4. **Have 2–3 other trusted operators independently run `dumptxoutset` at the same block height.** All `txoutset_hash` values must match exactly.

5. **Populate `m_assumeutxo_data`** in `chainparams.cpp` with the verified values.

6. **Update `chainTxData`** if stale:
   ```cpp
   chainTxData = ChainTxData{
       .nTime    = <BLOCK_TIMESTAMP_AT_SNAPSHOT_HEIGHT>,
       .tx_count = <NCHAINTX>,
       .dTxRate  = <ESTIMATED_TX_RATE>,
   };
   ```

7. **Distribute the snapshot file.** The Blackcoin UTXO set is much smaller than Bitcoin's (~1–3 GB vs ~12 GB). Host it on a trusted CDN or IPFS, and link it from the release notes.

8. **Document the user workflow** in the release notes:
   ```bash
   # After downloading the snapshot file:
   blackcoin-cli loadtxoutset /path/to/utxo-blk<HEIGHT>.dat
   ```

## 9. Summary

AssumeUTXO is **functionally complete** in Blackcoin More 284. The Bitcoin Core infrastructure is correctly inherited and extended with full PoS awareness:

- `Coin` serialization includes `fCoinStake` and `nTime` — snapshot data is PoS-complete.
- The UTXO hash commitment includes `fCoinStake` — the hash distinguishes PoS from PoW outputs.
- Snapshot load/validation handles all Blackcoin-specific fields transparently.
- Network magic prevents cross-chain snapshot misuse.
- The dual-`Chainstate` architecture in `ChainstateManager` supports concurrent PoS validation in the background.

**The only actions required to ship this feature:**
1. Generate a UTXO snapshot at a chosen height using `dumptxoutset`.
2. Verify the `txoutset_hash` with at least 2 independent operators.
3. Add one `AssumeutxoData` entry to `src/kernel/chainparams.cpp`.
4. Distribute the snapshot file alongside the new release.
